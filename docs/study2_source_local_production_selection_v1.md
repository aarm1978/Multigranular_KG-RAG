# Source-local full-production preparation selection v1

Prospective preparation only, using the unchanged source-local v0.4.1 source,
identity, endpoint, evidence and acceptance rules and specialized v0.4.2 requests
and owner consolidation. This does not authorize provider execution or a KG.

`python -m src.evaluation.source_local_specialized_production prepare` writes a
new ignored `var/study2_step13/source-local-specialized-production/v3/` directory.
Existing output is refused. The versioned `source-selection-manifest.json` is a
reusable baseline authority: every frozen corpus owner has a source record hash,
original/recovery lineage, complete selected unit identities, exact text hashes,
source provenance, and an immutable native context reference when preparable.
All source and implementation bytes are pinned and rechecked after preparation.
No historical artifact is rewritten or selected semantic output merged.

HydroShare uses recovery inputs for exactly the 20 recovered owners and original
inputs for the other 22. GitHub uses all historical owner bundles to recover the
complete eligible documentary authorities, preserving the existing file-level
exclusions and structured own-product version authorities. Hub uses complete
materialized `content_mdx`. All three historically unqueued pages are explicitly
included from the frozen corpus via the existing full-content adapter. Their
historical empty-reader status and lexical region diagnostics are recorded.
Dynamic-only pages can legitimately yield no assertions; supplying literal MDX
does not release dynamic, code-only, uncertain, or insufficient-evidence holds.
No new content eligibility or ontology decision is introduced.

Every preparable owner gets all three unchanged specialized groups. Exact
source-local identities, deterministic reuse, deferred assertions, abstentions,
and D-26 nonredundancy remain governed by v0.4.2 replay and consolidation.
No response is generated or replayed during preparation.

The validated 96 KiB selected-text and 1 MB provider-envelope margins remain
fail-closed. Owner context splitting is **not** silently introduced: v0.4.2
consolidation requires the same complete context across its specialized groups.
Blocked owners remain in the manifest, with their exact reason and available
source diagnostics. A partial queue is inspectable, but submission is forbidden
until a new complete preparation is approved and sealed. Fixing a blocked owner
requires a fresh output directory; never edit a sealed selection or queue.

`preflight --queue-sha256 HASH` checks all pins, native group reconstruction,
owner/group completeness, contexts, Batch lines, sizes and recorded cost inputs.
It writes `offline-preflight.json` once. If owner preparation is incomplete it
reports the blockers and does not initialize a provider execution. Otherwise it
runs the unchanged native Batch preflight. `submit`, `status`, `collect`, and
`review` reuse the existing native Batch journal and v0.4.2 owner consolidation.
Submission requires `--queued-token-limit` to be set to the researcher's actual
available provider queue capacity. It is not inferred from offline token estimates.

Estimates cover prepared requests only: native low/pooled/high/output-ceiling
byte heuristics with pinned Batch pricing, no assumed cache savings or retries.
They are neither measured token usage nor dollar authorization. Blocked-owner
costs are explicitly absent. No precision, recall or scientific quality claim is
made by preparation completeness or technical preflight.

The initial local attempts (`v1/`, `v2/`) were interrupted before sealing;
they remain untouched. The default fresh output is `v3/`. New Hub page seeds use
the native inventory and provider adapter without historical pilot-only metadata.
The invocation-local parser cache returns detached copies of identical bytes;
native ontology hash and version validation still runs on every read.
