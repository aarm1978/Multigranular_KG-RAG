# Step 14 prospective complete-component adjudication

The frozen reconciliation v1 baseline contains 1,355 provisional groups covering 3,777 source occurrences. Its unresolved memberships seed a traversal over shared original occurrence IDs. The incidence inventory includes explicit collective strict proposals (including held items), earlier supported complete candidates and contextual strict assessments, provisional targets and exact researcher-approved scopes. Identical memberships share one inventory entry with separate references for their origins. A component with one surviving candidate can still have evidence opposing it. Pair nominations and local distinct assessments remain evidence pointers; they do not extend an identity component. No historical votes, rankings or protection flags appear in model input.

A ready request contains the **entire** connected record set, exact source-local excerpts, per-artifact aliases, available granularity/version context and the deduplicated candidate memberships. The model may replace the alternatives with any evidence-supported complete partition. Every occurrence must belong to exactly one strict group, distinct singleton or abstention. The model supplies the semantic judgment. The mechanical checks cover complete partition membership, assignment-level source support, class and inventory compatibility, structured conflicts and exact human-approved scopes. Missing structured versions leave scientific interpretation to the quoted evidence. Free-text descriptions never allocate a canonical referent.

A validated complete partition is an automatic prediction eligible for later evaluation under a frozen production rule. The next decision ledger must explicitly record any supersession of a prior provisional target, including old and new exact memberships, supporting item references, validation contract and decision authority. Historical human-approved scopes are protected against splitting or enlargement. An independent bounded model-blind human evaluation remains the production gate. Optional cross-assignment leads retain original endpoints, model wording, evidence IDs and source bindings for later typed-relation adjudication. Each lead receives its own disposition. A partition can remain valid when an optional lead fails.

**Resource boundary.** One request may include up to 24 members and 96,000 serialized input-body bytes. The consumer also checks projected per-member output against the saved provider cap. Token scenarios use the observed extrema of input tokens per request byte and output tokens per occurrence in the ten completed v3 stress requests, including reasoning. This extrapolates beyond their maximum of 12 members. The cost scenario uses the repository's GPT-6.1 historical planning rates of $2.50 per million input tokens (cache-write scenario), $10 per million output tokens and half those rates for Batch. These are workload estimates with no assumed retries.

**Bounded staging.** For deferred components the inventory provides up to four candidate evidence readings with one shared occurrence. Each later reading must retain original citations and mark hypotheses crossing its boundary as open. The shared occurrence provides consistent evidence context across readings and conveys no identity. A single prospective final request must receive every original member, its decisive source spans, preserved contradictions, all cross-boundary alternatives and the provisional reading results, and return one complete-component partition. Prepare that request only if the assembled evidence and projected final output fit an explicitly verified budget. Missing evidence, a failed final consistency check or exceeding either the four-reading or final-request limit leaves the component unresolved. No staged request is in the dispatch file.

From the repository root, use `python -m src.evaluation.step14_component_adjudication` with `verify` to check pinned inputs and outputs, `inspect` to print the four pilot requests, and `pilot` for explicit live execution. The existing transport records immutable claims, receipts, usage and validation results. The `submit`, `status` and `retrieve` modes operate on one Batch of the remaining ready components. The ignored package resides at `var/study2_step14/component-adjudication/v1/`.
