# Step 14 final complete-component predictions

The v2 package references the 115 complete v1 predictions by original receipt and hash. It carries one new whole-component request for each v1 oversized or held component. The inventory and its historical references stay in v1. Each new request presents the original selected excerpts, source and occurrence aliases, exact distinct candidate sets, and explicit locked human-approved memberships. A text table stores repeated literals once. Each citation still binds to its original occurrence and source. Held v1 assignments supply their earlier evidence and reasoning as hypotheses for reconsideration.

The semantic decision belongs to the model. Compatible differences in configuration, deployment or time step can qualify a strict group. Each assessment distinguishes compatible qualifications, material conflicts, unresolved ambiguity and absence of a conflict. Direct member support, qualifying citations and contradictory citations retain separate roles. Material conflict or unresolved identity ambiguity requires separation or abstention. Output validation checks exact partition coverage, class/inventory and structured granularity compatibility, source bindings and protected membership. Mechanically invalid assignments retain their original text and affected occurrences. Independent assignments and supported leads across independent assignments survive. Missing or multiply assigned members remain mechanically unresolved. Model abstention is a final scientific outcome. The prediction report records old provisional memberships and proposed replacement indices for supersession. Independent model-blind evaluation applies to the automatic procedure.

The schema enumerates the complete entity alias set once and checks lead endpoints against the exact binding table locally. Offline preflight checks the repository's strict-schema limits, schema validity, serialized body bytes and context headroom. The supplied context and output limits are 1,050,000 and 128,000 tokens. The context check uses one token per serialized UTF-8 byte plus 2,048 framing tokens, and reserves the full output cap. Output caps round up to 1,024-token increments from twice the observed v1 95th percentile output tokens per occurrence, plus 2,048 reasoning tokens, capped at the model maximum.

Input estimates scale serialized request bytes by the pooled v1 input-token/byte ratio. Realistic output estimates scale occurrence counts by the pooled v1 output tokens per occurrence including reasoning. Large components extrapolate beyond the observed sample. Batch cost uses repository planning rates of $1.25/M input and $5/M output. The output-ceiling scenario holds estimated input fixed and consumes every reserved output token.

From the repository root use `python -m src.evaluation.step14_final_components verify` for offline verification. Use `submit`, `status` and `retrieve` on the same module for the single Batch. Preparation in a separate fresh directory is available via `prepare --root PATH`. The default ignored package is `var/study2_step14/component-adjudication/v2/`.
